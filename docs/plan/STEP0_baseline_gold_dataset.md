## 3. Baseline-аудит целевого демо-репозитория

Кандидаты (решение по §7): `tensorflow/docs` или `QGIS-Documentation`.

Что фиксируем в `data/reports/baseline_<repo>.md`:
1. Структура `docs/`, наличие ADR/API-ref/README.
2. Покрытие: доля публичных функций/классов с docstring (для Python-проекта анализа; для docs-репо — покрытие разделов).
3. Качество текущей документации: устаревшие разделы, разрывы ссылок.
4. Итоговая таблица «до/после» — точка отсчёта для демонстрации ценности системы.

Инструменты аудита: простой скрипт (pydocstyle/vulture-подобная эвристика + линтер ссылок). Для MVP хватит ~150 строк.

## 4. Gold Dataset

### 4.1 Схема записи (`data/gold/pairs/*.json`)

```json
{
  "id": "qgis-7912",
  "source_repo": "QGIS-Documentation",
  "pr_number": 7912,
  "pr_url": "https://github.com/QGIS/QGIS-Documentation/pull/7912",
  "category": "new_feature_doc",
  "trigger_kind": ["api_new", "adr_new"],
  "files_changed": ["docs/user/.../raster.rst"],
  "code_diff_summary": "…",
  "expected_docs_change": {
    "files": ["docs/..."],
    "human_written_text": "…",
    "change_type": "add|update|fix_typos|none"
  },
  "lang": "ru|en",
  "notes": "почему это хороший эталон"
}
```

### 4.2 Категории кейсов (равновесим выборку)

| Категория | Пример-источник | Ожидаемое поведение агента |
|---|---|---|
| `api_change` | QGIS PR #7912 (новый алгоритм обработки) | дополнить API-ref/руководство |
| `feature_doc` | TF PR #128355 (примеры TFLite) | добавить примеры в руководство |
| `typo_fix` | TF PR #128320 | **не комментировать** (noise-кейс) |
| `internal_refactor` | любой refactor без изменения публичного API | **не комментировать** (negative) |
| `adr_impact` | PR, меняющий архитектурное решение | предложить запись/правку ADR |
| `bootstrap` | проект без docs/ | суммарный обзор (см. §5) |

Целевой объём MVP: **30–40 кейсов**, из них ≥30% negative (агент должен молчать) — это главный страж против спама комментариев.

### 4.3 Как собираем
1. GitHub API: список merged PR, фильтр по изменению файлов в `docs/`.
2. Извлекаем diff кода (или source-PR) + human docs-diff.
3. Разметка категорий — вручную (2 человека), плюс LLM-преклассификация для скорости.

⚠️ Резервирование PR: если берём PR из открытых репо как «эталон», параллельно готовим **свой синтетический мини-репозиторий** (см. §7) — на нём безопаснее демонстрировать bootstrap и создавать тестовые PR с замечаниями лида (шаг 5 требует живых комментариев в тред — в чужом репо мы их оставлять не сможем).

## 5. Bootstrap-режим (первый запуск, docs/ нет или пуста)

Проблема: генерировать всю документацию сразу — плохо (контекст > лимита 3b-модели, низкое качество, нет HITL-гранулярности).

Решение — **поэтапный scaffold**:

```
BootstrapPlan (составляется детерминированным сканером, не LLM):
  Stage 1: структура docs/ + index + README-скелет          → draft PR #B1
  Stage 2: обзор архитектуры (по структуре пакетов)          → draft PR #B2
  Stage 3: API reference по модулям (чанк: 1 модуль = 1 секция) → draft PR #B3..#Bn
  Stage 4: ADR-скелеты по ключевым решениям (top-N)          → draft PR #B(n+1)
```

Правила:
- Каждый stage — отдельный draft PR → одобрение лида → следующий stage (HITL-цикл тот же, что для обычных PR).
- Порядок и состав чанков считает **детерминированный сканер** (tree walk, импорт-граф), LLM только пишет текст внутри чанка. Это снижает галлюцинации 3b-модели.
- Размер чанка ограничиваем: ≤N строк кода / ≤M символов контекста (подбираем на Ollama, фиксируем в конфиге).
- Статус bootstrap хранится в `.docagent/state.json` в ветке бота (resume после прерываний).

## 6. Триггеры: когда агент пишет, когда молчит

Детерминированный pre-filter (до обращения к LLM — экономия и предсказуемость):

**IGNORE (молчим):**
- typo-only правки (diff < порога, только орфография);
- изменения в CI/CD, тестах, formatting/lint-only;
- внутренние рефакторинги без изменения публичного API (см. маркер ниже).

**TRIGGER (пишем):**
- добавлены/изменены публичные символы: новые `def/class` без `_`-префикса, изменение сигнатуры, удаление публичного символа;
- изменения в моделях данных / схемах / эндпоинтах;
- изменения, влияющие на архитектурные решения (новые зависимости, смена подсистемы) → ADR-кандидат;
- правки, меняющие поведение, описанное в существующих docs (ищем пересечение changed-files × docs-references).

Маркеров в коде нет → выводим публичный API **эвристикой**: имена без `_` + явный `__all__` + экспорт в пакетах. Результат фильтруем LLM-верификацией («изменился ли контракт для пользователя?»). Порог чувствительности — в конфиге.

## 7. Контракт для Eval (шаг 6) — фиксируем сейчас

Метрики на gold set:
1. **Trigger precision/recall** — самое важное: не спамить vs не пропускать. Цель MVP: recall ≥ 0.8, precision ≥ 0.9 на negative-кейсах.
2. **Faithfulness** — все упомянутые имена функций/параметров реально существуют (проверяется детерминированно против AST — бесплатно и надёжно).
3. **Structure validity** — правка попадает в правильный файл/секцию docs/.
4. **Semantic similarity** — cosine(embeddings human_text vs generated_text); эмбеддинги — локально (например, `nomic-embed-text` через тот же Ollama).
5. **LLM-as-judge** — rubric 1–5 (полнота/точность/стиль); отдельно оценивает другая модель-судья, промпт судьи версионируется.
6. Онлайн-метрики (шаг 5+): approve-rate, median reject-rounds, time-to-approve.

Формат прогонов: `eval run --model qwen2.5-coder:3b --prompt-version v3 --dataset gold-v1` → отчёт в `data/reports/`. Промпты и модели версионируются именно поэтому (§2, папка `prompts/`).
