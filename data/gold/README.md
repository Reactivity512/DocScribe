# Gold Dataset v1

Эталонный набор «diff PR → правильная документационная правка». Это ground truth
для шага 6 (Eval) и фикстуры для шагов 1–3.

## Состав

| Показатель | Значение |
|---|---|
| Всего кейсов | **44** (вилка плана 30–40 осознанно превышена по решению лида) |
| Negative (агент обязан молчать) | **19 = 43%** (минимум 30%) |
| Bootstrap-стейджей | **5** (было 3) |
| Языки | ru: 21, en: 23 |
| Категории | 10 из 10 обязательных |
| Источник | synthetic (модели по мотивам реальных PR доноров) + bootstrap_scan |

Распределение категорий: `api_change` 6, `readme_update` 6, `internal_refactor` 5,
`bootstrap` 5, `feature_doc` 4, `adr_impact` 4, `typo_fix` 4, `ci_test_only` 4,
`style_format_only` 4, `docs_only` 2.

Дополнительные срезы (labels/severity): `hard_for_small_model` 7, `edge` 12,
`multi_file` 7, `noise` 10, `breaking` 3, `needs_illustration` 2;
severity — high 16 / medium 22 / low 6.
По типу правки: `add` 12, `update` 13, `none` 19. Правок касается 17 уникальных
файлов документации, у 8 кейсов указан донорский PR.

## Структура

```
data/gold/
├── README.md          # этот файл
├── schema.json        # JSON Schema 2020-12 (gold-v1)
├── cases/             # 44 файла gold-NNN.json
└── raw/               # полные патчи (пока пусто: используются inline-diff'и)
```

Все кейсы описывают вымышленную Python-библиотеку `demopkg`. Это осознанно:
нет зависимости от чужих репозиториев, нет вопросов с лицензией, а те же самые
изменения позже можно руками завести в наш демо-репозиторий и прогнать живой
HITL-цикл (шаг 5). Донорские PR указаны в `source.donor_reference` как источник
идеи и эталон стиля.

## Ключевые поля схемы

| Поле | Зачем | Какая метрика Eval |
|---|---|---|
| `expected_behavior` | `write_docs` / `stay_silent` / `escalate_bootstrap` | Trigger precision/recall |
| `trigger_kind` | причина срабатывания (`api_new`, `behavior_changed`, …) | spec для MCP-инструмента `should_update_docs` |
| `severity` | цена ошибки триггера | вес в сводном скоре |
| `code_change.diff` | вход агента (unified diff или bootstrap-снимок) | — |
| `docs_change.target_files` + `target_section` | куда должна попасть правка | Structure validity |
| `docs_change.human_written_text` | эталон человека | Semantic similarity, LLM-as-judge |
| `must_include` | обязательные факты (имена, параметры, значения) | Faithfulness (детерминированно) |
| `must_not_include` | галлюцинации-ловушки | Anti-hallucination (детерминированно) |
| `labels` | `negative`, `edge`, `hard_for_small_model`, … | срезы в отчётах |

## Как устроены negative-кейсы (анти-спам ядро)

19 кейсов, где правильный ответ — не создавать ни PR, ни комментарий:

* `typo_fix` (4) — орфография в README, в docstring, пунктуация в prose, плюс
  **ловушка**: исправление опечатки в имени приватного атрибута `_toke` → `_token`
  (имя символа изменилось, контракт — нет);
* `internal_refactor` (5) — модуль `_internal`, добавление type hints, перемещение
  приватного модуля, переписывание тестов, внутренняя оптимизация;
* `ci_test_only` (4) — workflow, coverage, flaky-тест, pre-commit;
* `style_format_only` (4) — массовое форматирование (огромный diff при нулевом
  смысловом изменении), lint-only, реформатирование docstring без смены смысла
  и переименование локальных переменных (`idx`, `padded`) — детектор обязан
  различать scope и не реагировать на имена вне контракта;
* `docs_only` (2) — автор сам правил документацию.

## Bootstrap: конвейер из 5 стейджей

Первый запуск на проекте без `docs/` разбит на последовательные stage'ы — каждое
срабатывание даёт отдельный draft PR, одобряется лидом отдельно, следующий
стейдж запускается только после merge предыдущего. Это снимает проблему «сразу
написать документацию на весь проект» и ограничивает объём контекста для
qwen2.5-coder:3b.

| Stage | ID кейса | Язык | Артефакт | Прямое ограничение (must_not_include) |
|---|---|---|---|---|
| 1. Каркас | gold-042 | ru | `docs/index.md` + пустые скелеты разделов | полное описание функций, ADR-тексты |
| 2. README | gold-040 | ru | установка + quickstart из `pyproject`/кода | альтернативные способы установки, выдуманные env-имена |
| 3. API-ref | gold-043 | en | чанк по одному модулю (`demopkg.exporters`) | функции, которых в модуле нет |
| 4. ADR | gold-044 | ru | скелеты ADR по кандидатам из структуры кода | причинные формулировки («потому что команда выбрала…») |
| 5. Changelog | gold-041 | en | история по git log | даты релизов, номера версий без тегов |

Порядок выполнения в графе (шаг 3): `1 → 2 → 3 → 4 → 5`, где 3 итеративно
повторяется по модулям. Порядок id в файлах не совпадает с порядком стейджей —
сопоставление только через `source.reference`.

## Воспроизведение и проверка

```bash
python scripts/build_gold_dataset.py --force   # пересобрать все 44 кейса
python scripts/validate_gold.py                # отчёт
python scripts/validate_gold.py --strict       # CI-гейт: exit != 0 при проблемах
```

Валидатор проверяет JSON Schema плюс инварианты, которые в схеме выразить
громоздко: согласованность `category ↔ expected_behavior`, наличие label
`negative` у всех молчаливых кейсов, принадлежность `target_files` зоне `docs/`
или `README.md`, присутствие каждого `must_include` в эталонном тексте (пути
проверяются по `target_files`), отсутствие `must_not_include` в эталоне,
похожесть `diff` на unified diff и баланс выборки.
